# Attack Reproduction

## 1. Objective

This document describes how HashDoS-style collision behaviour is reproduced in HashDoS-Lab using controlled Java hash collision inputs.

The objective is to demonstrate the computational impact of hash collisions on a deliberately vulnerable hash table and compare its behaviour with alternative implementations.

All experiments are performed against the local application in a controlled testing environment.

## 2. Java String Hash Collisions

Java's `String.hashCode()` method calculates a hash value based on the characters in a string.

Different strings can produce the same hash code. Such strings are known as hash collisions.

HashDoS-Lab uses the well-known `"Aa"` and `"BB"` collision pattern to generate distinct strings with identical Java hash codes.

For example:

- `"Aa"` and `"BB"` have the same hash code.
- `"AaAa"` and `"BBBB"` also have the same hash code.

The generator creates keys using combinations of these patterns.

## 3. Collision Key Generation

The collision keys are generated by:

`io.github.ashan.hashdoslab.payload.CollisionKeyGenerator`

The generation logic uses the following pattern:

`"Aa".repeat(i) + "BB".repeat(count - i)`

Each generated key is distinct, but all generated keys share the same Java hash code.

This makes them suitable for controlled collision testing.

## 4. Reproducing the Attack

### 4.1 Start the Application

Run the Spring Boot application locally.

The application should be available at:

`http://localhost:8080`

### 4.2 Run Collision Analysis

Send the following request:

**Endpoint**

`POST /api/v1/analysis/compare`

**Request body**

```json
{
  "keyCount": 1000
}
```

This endpoint compares traversal behaviour between normal generated keys and collision-heavy keys.

### 4.3 Compare Hash Table Implementations

Send the following request:

**Endpoint**

`POST /api/v1/analysis/compare-engines`

**Request body**

```json
{
  "keyCount": 1000
}
```

This endpoint evaluates the insertion performance of:

- VulnerableHashTable
- JavaHashMapAdapter
- HardenedHashTable

The same collision key set is used across the three implementations to make the comparison meaningful.

## 5. Expected Vulnerable Behaviour

The vulnerable implementation uses:

- A fixed-size bucket array.
- Separate chaining with singly linked lists.
- Tail insertion that traverses the existing linked list.
- No resizing or treeification.

When all keys are assigned to the same bucket, each insertion must traverse the previously inserted nodes.

For `n` colliding keys, the expected total traversal count is:

`n(n - 1) / 2`

For 1,000 colliding keys:

`1000 × 999 / 2 = 499,500`

This demonstrates quadratic insertion behaviour.

## 6. Observed Results

### 6.1 Collision Analysis

For a request containing 1,000 keys, the observed result was:

| Metric | Result |
|---|---:|
| Key count | 1,000 |
| Normal input traversal count | 31,842 |
| Collision input traversal count | 499,500 |
| Traversal difference | 467,658 |
| Traversal ratio | 15.69x |

The normal input is not guaranteed to be collision-free. Its traversal count represents the actual behaviour observed during the experiment.

The collision input produces exactly 499,500 traversal operations, matching the theoretical calculation.

### 6.2 Engine Performance Comparison

For a request containing 1,000 collision keys, the observed results were:

| Metric | VulnerableHashTable | JavaHashMapAdapter | HardenedHashTable |
|---|---:|---:|---:|
| Average insertion time | 556.74 ms | 63.99 ms | 47.61 ms |
| Median insertion time | 498.70 ms | 46.82 ms | 44.94 ms |
| Entry count | 1,000 | 1,000 | 1,000 |

The vulnerable implementation required significantly more time to insert the collision-heavy input.

All three implementations successfully stored 1,000 entries.

## 7. Measurement Methodology

The engine comparison uses:

- 5 warm-up iterations.
- 15 measurement iterations.
- Fresh hash table instances for each run.
- The same collision input across all implementations.
- Rotating engine execution order to reduce fixed execution-order bias.
- Average and median insertion time measurements.

Correctness verification is performed outside the timed insertion section.

The measurements are collected using an in-application timing harness. They are not intended to be a substitute for a dedicated benchmarking framework such as JMH.

## 8. Important Limitations

- Execution time depends on JVM warm-up, JIT compilation, garbage collection, operating system activity, and hardware.
- The reported timing values represent one observed test environment and are not universal performance guarantees.
- Java HashMap may use tree-based collision handling under certain conditions, depending on the JDK implementation and bucket characteristics.
- The experiment demonstrates the behaviour of the project's deliberately vulnerable implementation, not every hash table implementation.

## 9. Reproduction Summary

The experiment demonstrates that specially constructed Java String hash collisions can cause quadratic insertion behaviour in the vulnerable implementation.

The measured traversal count confirms the theoretical result for 1,000 colliding keys.

The same collision input is then used to compare the vulnerable, standard Java HashMap-based, and hardened implementations.
